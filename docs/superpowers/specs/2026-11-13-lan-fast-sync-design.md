# 局域网加速 + iCloud 兜底同步设计

## 目标

让 iPhone 快捷指令在同一 Wi‑Fi 下记录喝水时，Mac 菜单栏应用通常在一秒左右更新；离开同一网络、Mac 睡眠或局域网请求失败时，仍由现有 iCloud 文件同步在之后补齐。两条通道共用同一个事件 ID，不能重复计数。

用户已经选定“局域网加速、iCloud 兜底”的组合。这里不再考虑把局域网作为唯一通道，也不引入开发者服务器或第三方中继。

## 目标与非目标

目标：

- 同一 Wi‑Fi 下，手机记录后 Mac 快速更新今日水量和逐次记录。
- 手机仍先把事件写入 iCloud，断网、跨网络或 Mac 不在线时不丢记录。
- 局域网和 iCloud 任一路先到，另一路后到都不会重复。
- 设置一次后自动发现 Mac 的局域网地址，不需要每次改快捷指令。
- 关闭 iCloud 同步时停止局域网监听，不在后台开放端口。
- 继续支持 macOS 13 和现有 `state.json`、CSV、iPhone 事件文件。

非目标：

- 不通过局域网同步提醒时间、暂停状态、彩带动画或通知队列。
- 不提供公网访问、账号体系、中继服务或跨公网直连。
- 不重做历史页面、导出和现有菜单栏交互。
- 不把 iPhone 快捷指令改成独立的 iOS 应用。

反目标：

- 局域网失败导致手机记录没有落到 iCloud。
- 同一杯水在两条通道各算一次。
- 未认证的局域网设备可以写入饮水记录。
- 每次 Mac IP 变化都要求用户重新配置快捷指令。

## 方案比较

1. **局域网优先、iCloud 镜像（采用）**：快捷指令先保存 iCloud 事件，再向 Mac 的局域网端点发送同一事件。Mac 收到后立即合并并写回共享 CSV；iCloud 副本之后到达时只做去重。它解决当前上传延迟，同时保留跨网络能力。
2. **只优化 iCloud**：不改代码，只提示用户检查网络和 iCloud。实现零成本，但无法控制 Apple 的上传延迟，也不能保证体验稳定。
3. **公网中继或 WebSocket**：速度最快且跨网络最可靠，但需要账号、服务器、隐私说明和运维，违背“不使用第三方后台”的产品方向。
4. **只走局域网**：延迟最低，但离开家或 Mac 睡眠时记录无法到电脑，不能作为唯一方案。

## 数据流

1. 快捷指令生成一次唯一事件，格式与现有 `DrinkSyncEvent` 一致。
2. 快捷指令先把事件保存到 iCloud 的 `Sync/Events`，确保无论后续发生什么都有一条持久记录。
3. 快捷指令读取 `Sync/Devices` 中每台 Mac 的独立配置，在手机和 Mac 处于同一子网时向其中一台或几台发送同一份事件 JSON。
4. Mac 的局域网接收端校验令牌和事件内容，把事件放入本地 outbox，立即合并到 `state.json`，再尽力写回共享 CSV 和今日汇总。
5. iCloud 事件文件随后到达时，Mac 按事件 ID 忽略重复副本。

任一通道失败都不能回滚已经保存到另一通道的记录。

## Mac 接收端

- 使用系统 `Network.framework` 的 TCP 监听器，不增加第三方依赖。
- 只接受 `POST /v1/drink`，请求体上限 8 KB，连接处理完立即关闭。
- 默认从端口 47832 开始尝试，端口占用时顺延到附近可用端口；实际地址写入这台电脑自己的 `Devices/<deviceID>.json`。
- 同时发布稳定的 Bonjour 主机名、当前局域网 IPv4、`/24` 前缀和实际端口，供快捷指令按优先级选择。
- 完全没有可用局域网地址时只发布 iCloud 配置，快捷指令跳过加速请求。
- 令牌为首次启用时生成的随机值，保存在本机并写入这台电脑自己的设备文件。请求必须带 `Authorization: Bearer <token>`。
- 应用退出、关闭 iCloud 同步或关闭局域网加速时停止监听。
- 首次监听可能触发 macOS 防火墙确认；Info.plist 增加局域网用途说明。

局域网事件进入主线程后复用现有合并逻辑，不另建一套记录模型。事件先写入 outbox，再更新内存和 `state.json`；即使 iCloud 暂时不可写，Mac 本机也能立即显示。

## 地址稳定性与网络场景

用户不需要理解或手动填写 IP。地址按以下顺序处理：

1. **稳定名称优先**：使用 Mac 的本地 Bonjour 主机名，例如 `bobos-macbook-pro.local:47832`，写入设备文件的 `lanURL`。这是主地址；路由器重新分配 IP、Mac 从 Wi‑Fi 切到 Ethernet、或离开再回家时，这个名字通常不变。
2. **当前 IP 备用**：Mac 同时把当前私有 IPv4 写入设备文件的 `lanFallbackURL`。如果主机名在当前网络不可解析，快捷指令可以在同一子网内尝试这个备用地址。
3. **iCloud 最终兜底**：两个局域网地址都不可用时，之前已经保存到 iCloud 的事件继续按原路径到达。

Mac 会监听网络变化和唤醒事件。网络切换、IP 变化、端口变化或主机名变化后立即重写自己的设备文件，并保持访问令牌不变，避免手机端需要重新配置。快捷指令每次运行都会重新读取设备目录。

具体场景：

- **路由器重新分配 IP**：稳定名称不变；即使手机手里的旧 IP 过期，仍优先使用名称。
- **Wi‑Fi 与 Ethernet 切换**：Mac 重新选择当前活动的私有地址并更新配置；监听器保持在同一个应用生命周期内。
- **Mac 睡眠或应用退出**：没有局域网响应，手机记录仍在 iCloud；Mac 唤醒或启动后合并。
- **手机离开同一网络**：手机拿到的本地地址不在 Mac 发布的子网内，跳过局域网请求，直接走 iCloud。
- **访客 Wi‑Fi 开启设备隔离**：局域网请求失败，iCloud 继续；不要求用户改路由器。
- **VPN 或多网卡**：忽略回环、链路本地、公网地址和明显不属于当前主网络的接口，优先选择当前活动网络上的私有 IPv4。
- **端口被占用**：自动顺延端口并把实际端口写回配置；手机下次运行自动使用。
- **主机名冲突或用户改了电脑名**：Mac 发布新的本地名称；手机读取新配置后自动切换。设置页显示当前地址，便于排查。
- **防火墙首次拦截**：用户在系统提示中允许一次；拒绝时只损失局域网加速，iCloud 不受影响。
- **多台 Mac 使用同一 iCloud 账户**：每台 Mac 发布独立设备文件，手机选择当前网络中的一台；其他电脑通过共享事件文件汇合。详细规则见下一节。

如果系统允许，快捷指令会先尝试稳定名称，再尝试当前 IP；如果 Shortcuts 的网络动作必须中断流程，则只尝试当前最可信的一个地址，并确保 iCloud 事件已经先保存。这个取舍会在真机验证时固定下来，不把不确定的网络错误留给日常使用。

## 多台 Mac

多台 Mac 不能共同覆盖同一个端点字段。每台电脑使用独立的设备 ID，并在 `Sync/Devices/<deviceID>.json` 发布自己的地址、备用地址、子网、令牌和最近在线时间：

```json
{
  "schemaVersion": 1,
  "deviceID": "mac-7F2A...",
  "name": "BOBO 的 MacBook Pro",
  "role": "auto",
  "lanURL": "http://bobos-macbook-pro.local:47832",
  "lanFallbackURL": "http://192.168.1.20:47832",
  "lanSubnet": "192.168.1",
  "lanToken": "…",
  "lastSeen": "2026-11-13T11:30:00+08:00",
  "lastSeenEpoch": 1763004600
}
```

手机快捷指令读取 `Devices` 文件夹，只保留与当前手机 IP 同子网的设备，然后按以下顺序选择：

1. 用户标记为“优先接收”的电脑；
2. `lastSeenEpoch` 最大的电脑；
3. 设备名称的稳定排序。

如果没有标为优先的电脑，就自动选择，不需要用户理解设备 ID 或 IP。用户也可以在一台 Mac 的设置里把“优先接收”打开；多台同时打开时仍按最近在线时间决出，不会因为设置冲突而写错记录。

如果 Shortcuts 支持在一次运行中继续处理失败，手机会依次尝试同网络的其他电脑；否则只尝试选中的一台，其余电脑依靠共享事件文件同步。无论哪条路径，手机都已经先保存了 iCloud 事件。

### 多 Mac 的共享数据

- 每台 Mac 的局域网事件除了写共享 CSV，还要写入 `Sync/Events/mac-<deviceID>-<eventID>.json`。这样即使两台 Mac 同时追加 CSV 导致 iCloud 选择其中一个版本，事件文件也不会丢。
- 所有 Mac 读取 `Events` 和现有共享 CSV，按事件 ID 去重；同一杯水被两台电脑收到也只保留一条。
- 两台 Mac 在同一时刻各点一次，是两个不同的事件 ID，即使水量和时间相同也必须保留两条；所有电脑最终都显示这两条。
- 同一次记录通过局域网和 iCloud 各到一次，是同一个事件 ID，只保留一条。撤销其中一台电脑上的某条记录时，也只删除对应的记录 ID。
- `today-summary.json` 和 `settings.json` 继续作为兼容缓存，允许短暂被不同 Mac 覆盖；饮水记录本身以 `Events` 为准，不能依赖单一汇总文件。
- 手机在同一 Wi‑Fi 下可以快速更新一台 Mac；其他 Mac 可能在 iCloud 到达后更新，但最终记录一致。
- 如果电脑分布在不同网络，手机只走当前子网内的局域网通道，其他电脑仍通过 iCloud；不会向公网发起请求。
- 设备文件是各自写入、互不覆盖的；长期离线的旧设备文件不影响选择，手机会跳过无效或明显过期的地址并回退 iCloud。

### 多 Mac 的可见状态

设置页显示这台电脑的设备名称、当前地址和“优先接收”开关。应用不会自动删除其他电脑的设备文件；用户换电脑或重装系统后，旧文件最多让手机多尝试一次地址，失败后仍会回退 iCloud。

## 设备标识与历史显示

来源字段只使用英文 `iphone` 或 `mac`，不把中文写进同步数据：

- 手机事件：`source: "iphone"`，界面默认显示 `iPH`；
- 电脑事件：`source: "mac"`；
- 具体设备另存 `deviceID`、完整 `deviceName` 和紧凑 `deviceShortName`；
- 每台 Mac 的设备 ID 使用硬件 UUID 加安装实例随机后缀，避免克隆系统后重名；
- 每台 Mac 默认获得最短的可用编号 `M1`、`M2`、`M3`；编号冲突时后加入的电脑自动顺延；
- 电脑后缀可以在设置里改成 1～8 个 ASCII 字母或数字，例如 `OFFICE`、`HOME`、`MBP`；保存时检查是否与其他在线电脑重名，`iPH` 保留给 iPhone；
- iPhone 后缀固定为 `iPH`，不参与电脑编号；
- 旧事件中的 `iphone-shortcut`、`phone`、`Mac` 等来源继续兼容读取，展示时归入 `iphone` 或 `mac`。

历史列表只显示紧凑后缀，避免挤占时间和水量：

- `10:58 · 197ml · M1`
- `11:02 · 197ml · M2`
- `11:06 · 197ml · iPH`

完整设备名放在鼠标悬停提示和导出文件里，例如 `BOBO 的 MacBook Pro`。旧记录没有紧凑后缀时继续显示原来的“电脑”或“手机”分类。CSV 的来源列只写 `iphone`/`mac`，具体设备信息放在事件 JSON 和导出文件的独立设备列中，避免来源字段混入中文或长设备名称。

重命名只改变显示后缀，不改变 `deviceID`，因此不会把历史记录拆成两杯水。Mac 同步时会根据设备文件更新本机历史里同一 `deviceID` 的后缀；设备文件已经不存在时，保留记录当时的后缀。两台电脑同时起名重复时，后保存的一端会收到重名提示；如果重名是在设备文件同步后才发现的，两台电脑按 `deviceID` 稳定排序，后一台自动追加数字并重新发布，避免长期同名。

## 快捷指令

- 在现有菜单和结果提示之间保留原有行为，不新增第二个日常使用的快捷指令。
- 读取 `Sync/Devices` 中每台 Mac 的设备文件；目录不存在时跳过局域网加速，继续走 iCloud。
- `lanURL` 是稳定名称地址，`lanFallbackURL` 是当前 IP 地址；快捷指令不需要用户填写地址。
- 在“查看今日记录”分支不发送事件。
- 在记录分支先保存 iCloud 事件，再比较手机 Wi‑Fi IPv4 与 `lanSubnet`。相同子网且配置完整时才发送局域网请求。
- 请求体直接使用刚保存的事件 JSON，避免再生成第二个 ID。
- 局域网成功时提示“已同步到电脑”；跳过或失败时提示记录已保存、将通过 iCloud 补齐。
- 快捷指令网络动作失败不能阻止 iCloud 保存。实现时验证 Shortcuts 的错误提示行为；如果系统动作无法静默失败，就把局域网请求放在最终确认之后，并只在同一子网预检通过后执行。

## 兼容与配置

- 新增 `LanDeviceRecord` 写入 `Sync/Devices`；`settings.json` 继续只保存每日目标和默认杯量，避免多台 Mac 互相覆盖端点。
- 新安装默认开启 iCloud 同步和局域网加速；旧设置缺少局域网开关时按开启处理，用户可以在设置中关闭。
- 设置页新增“同一 Wi‑Fi 下加速同步”开关，并显示当前局域网地址、设备名称或“仅 iCloud”状态。
- 无需重新扫码配置；手机下次运行快捷指令时从 `Devices` 读取当前电脑地址。
- 旧版快捷指令继续可用，只是仍走 iCloud。Mac 应用和快捷指令需要成对更新才能获得加速。

## 错误处理

- 手机不在同一子网：不发起局域网请求，继续 iCloud。
- Mac 睡眠、应用退出或端口不可达：局域网请求超时/失败，iCloud 记录仍在。
- Mac 收到无效令牌、非法水量或畸形 JSON：返回 4xx，不写入任何数据。
- iCloud 写入失败：局域网事件仍保存在 Mac outbox，现有补传机制继续工作。
- iCloud 和局域网在极短时间内同时到达：按事件 ID 合并，保留一条记录。

## 测试

- 设备文件新旧格式往返，地址字段缺失时仍可读取并安全跳过。
- 局域网地址选择忽略回环、链路本地和公网地址。
- 模拟 IP 变化后稳定名称保持不变，设备文件的当前 IP 和端口会更新。
- 端口占用时选择下一个可用端口，并把实际端口写入配置。
- 没有局域网地址、手机不在同一子网、VPN 和访客网络隔离时都只退回 iCloud。
- 两台 Mac 各自发布设备文件，手机按优先标记、最近在线时间和设备名称选出同一台；设备文件互不覆盖。
- 两台 Mac 收到同一事件时，只产生一条记录；共享 CSV 冲突时仍能从独立事件文件恢复。
- 新事件来源字段严格为 `iphone` 或 `mac`，同时保留设备 ID、完整设备名和 `M1`/`M2`/`iPH` 这类紧凑显示名；旧来源仍能归一化显示。
- HTTP 请求解析覆盖正常 POST、超长请求、错误路径、无令牌、错误令牌和非法事件。
- 同一事件重复提交只产生一条饮水记录；局域网先到、iCloud 后到和反向顺序结果一致。
- 快捷指令静态校验确认读取局域网配置、先保存事件、再发送同 ID 请求。
- 构建后实际启动应用，从设置读取地址和令牌，用本机请求验证成功、重复提交和关闭开关后拒绝连接。
- 在 iPhone 镜像/真机中运行更新后的快捷指令，确认同一 Wi‑Fi 快速更新、断开 Wi‑Fi 后仍由 iCloud 补齐。

## 需要保留的现有行为

- `state.json` 本机缓存和撤销逻辑不变。
- 共享 CSV 的既有手机、Mac 事件与旧 `iphone-amounts.txt` 兼容逻辑不变。
- 新手机记录使用 `iphone` 来源并显示 `iPH`；旧 `iphone-shortcut` 记录仍归入手机分类。
- 应用沙盒关闭、无开发者账号和零外部依赖的构建方式不变。

## 发布范围

这次作为同步体验升级发布，应用版本提升到 1.2.0，同时更新内置快捷指令、安装说明和同步状态文案。旧的 iCloud-only 快捷指令仍可安装，但不会获得局域网加速。
